# 显存暴涨原因分析和修复方案

> **version=20261106.1**
>
> 适用范围：`/3d` 星空视图，点击节点后显存从约 2GB 涨到约 4GB 并接近卡死的现象。
> 本文档为**分析结论 + 修复设计 + 实施记录**，P0/P1 修复均已落地并实测通过（显存稳定在 2GB 以下）。
> 约束基线：`Memory.md`（跨场记忆能力）与 `鉴权升级方案.txt`（角色/副本/房间隔离）必须原样保留。

---

## 0. 结论速览

| 项目 | 结论 |
|---|---|
| 根因 | **图谱节点实例被重复创建**，不是渲染参数、材质、bloom 或 three.js 版本问题 |
| 触发条件 | `updateNodeIncremental` 的缓存查找键与写入键不一致，本场已有节点被误判为"新节点" |
| 放大机制 | ① 广播扇出到 3 个房间 ② URL 自动聚焦形成 `/click → 广播 → 重载 → /click` 回环 |
| 单项最大显存开销 | **标签 CanvasTexture**（每节点 0.67–1.33 MB，250 节点 167–333 MB，且没有任何缓存） |
| 卡顿主因 | `updateEventHorizonVisibility` 点击后对**全图每节点重建标签纹理** + `for...in nodeCache` 的 O(N²) 全表扫描 |
| 修复原则 | 只消除浪费与重复，**不设节点数硬上限，不改任何业务语义** |

关于"250 节点 2G / 流畅 4G"：这是 **bak 版当时的实测断言**，不是产品规格。新版叠加了跨场 `[chat]` 记忆、接触面距离计算、用户副本三级回退，节点平均开销必然高于 bak。因此本方案**不采用任何数字阈值**，只做"消除浪费"类优化。

## 1. 已排除的方向

上一轮已完成渲染管线的逐项比对，以下因素在 `main.py` 与 `bak/main.py`、`static/js/3d_main.js` 与 `bak/static/js/3d_main.js` 之间**完全等价**，**不是根因**：

- `nodeThreeObject` 的构建流程
- 材质与贴图（`zhen/youzhen/duizhen/glaxy`）
- Bloom 后处理配置
- `nodeResolution`
- `.env` 中的 `HORIZON_DETAIL=0`、`MAX_EYES=40`（两版一致）
- `get_all_active` 函数体（两版逐字节相同）

`three.min.js` 从 r110 升级到 r128 **是放大器而非根因**：它提高了单张纹理的 GPU 侧成本，使同样的重复实例问题表现得更剧烈。

## 2. 显存开销拆解

每个节点在 `nodeThreeObject`（`static/js/3d_main.js:3533-3647`）中会被创建：

```
1 x THREE.Group
   |- 星体 Sprite  (贴图有 nodeTextureCache 复用，开销约 0)
   |- 标签 Sprite  (纹理无任何缓存，每个实例独立)
2 x SpriteMaterial
2 x 纹理
```

标签纹理由 `createTextTexture()`（`static/js/3d_main.js:1237`）生成，参数为 `scale = 4`（超采样，`:1263`）且尺寸对齐到 2 的幂（`:1288-1289`）。

实测估算（`ctx.font = 128px`，单行，含 padding `6*4`）：

| 标签字符数 | 原始尺寸 | 2 的幂对齐后 | 单节点显存 | 250 节点合计 |
|---|---|---|---|---|
| 5 字 | 432 x 200 | 512 x 256 | 0.67 MB | 167 MB |
| 10 字 | 816 x 200 | 1024 x 256 | 1.33 MB | 333 MB |

> **关键点**：标签纹理是显存占比最大的**单项**，且**完全无缓存**——每次创建都是全新的 canvas 绘制 + GPU 纹理上传。

剩余的 2GB 由 WebGL 帧缓冲、bloom 后处理链、d3 几何/索引缓冲构成。但 **2G→4G 的翻倍只能来自"对象数量翻倍"**，因为渲染侧所有配置都已确认等价。

## 3. 根因链（5 条放大路径，均已逐行验证）

### 路径 1（核心）：缓存键不一致导致误判"新节点"

三处对 `nodeCache` 的键使用**互不统一**：

| 位置 | 代码 | 使用的键 |
|---|---|---|
| 写入 | `static/js/3d_main.js:1607` `nodeCache[node.node_id] = merged` | `node_id`（字符串标题） |
| 写入 | `static/js/3d_main.js:2209` `nodeCache[data.node_id] = data` | `node_id` |
| 查找 | `static/js/3d_main.js:1813` `let cacheNode = nodeCache[sid] \|\| nodeCache[nid]` | **先试 `serial_id`（数字）** |

`sid` 是数字型 `serial_id`，而 `nodeCache` 中从未以它为键写入过，因此 `nodeCache[sid]` **必然 miss**；虽然紧接着有 `|| nodeCache[nid]` 兜底，但当 `nid` 与 `node_id` 因字段命名差异（`本事件标题` / `node_id`）不一致时同样 miss，于是落入 `else` 分支。

### 路径 2：miss 后走"新节点并入"分支

`static/js/3d_main.js:1834-1868`：

```js
} else {
    console.warn(`[SocketIO] 警告：未找到缓存节点，作为新节点增量并入缓存...`);
    cacheNode = Object.assign({}, uNode);
    ...
}
// 之后：
let gNode = graphNodes.find(n => n.serial_id === sid || n.id === nid || n.node_id === nid);
if (!gNode) {
    gNode = Object.assign({ id: nid }, cacheNode);
    ...
    pendingNewNodes.push(gNode);   // <-- 真正的新 THREE 对象
}
```

对比 `bak/static/js/3d_main.js:1456-1458`：**bak 版此处只打印警告，不创建节点**。

进入 `pendingNewNodes` 就会触发 `nodeThreeObject` → 新建 Group + 2 Sprite + 2 Material + 2 CanvasTexture。**这就是显存翻倍的直接来源。**

> 注意：这段"循环末一次性并入"的逻辑本身是**必须保留**的——`鉴权升级方案.txt` 附录"无限重绘"修复明确要求 `node_created` 走增量且依赖它；`Memory.md` §1.1 也要求跨场 `[chat]` 节点进图。所以要修的是**判定条件**，不是删除通道。

### 路径 3（放大）：广播扇出到 3 个房间

`main.py:1867-1883`：

```python
rooms = {public_room(owner_id), private_room(owner_id)}
rooms.add(public_room(field_owner_id))
for room in rooms:
    await sm.emit(event, node, room=room)
```

同一个 `node_id` 可能被前端收到多次，每次都跑一遍路径 1/2，重复实例数被乘。

### 路径 4（放大器）：URL 自动聚焦回环

`static/js/3d_main.js:1765-1778`：

```js
const urlSerialId = urlParams.get('serial_id');
if (urlSerialId) {
    setTimeout(() => {
        if (window.handleSearchResultClick) {
            window.handleSearchResultClick(urlSerialId, null, urlMaxEyes);
        }
    }, 1000);
}
```

这段位于 `fetchAndRenderGraph` 内。而 `loadInitialData()` 会在 `node_deleted`、`field_deleted`、巡航等场景被调用，于是形成：

```
/click -> 后端重排 -> node_updated 广播 -> 前端 updateNodeIncremental
       -> 若触发重载 -> fetchAndRenderGraph -> 1 秒后又打 /click -> 循环
```

注意同函数上方 `:1735` 已经有 `__loadState.hasAutoFitted` 做"仅首帧"保护，但 **URL 聚焦这一段没有同样的保护**。

### 路径 5：`promote_all_weights` 中跨场节点参与重排

`main.py:1218-1225` 与 `main.py:1265`：

```python
extra_nodes=extra_nodes
```

`bak/main.py` 只把跨场节点以 `distance=0` 追加展示，不参与权重重排。新版将其并入 `promote_all_weights`，配合 `core/database.py:1823-1826` 的"大股东补充查询"和循环内 `get_node_by_id`，形成 N+1 查询压力。

> 这一条**必须保留**：`Memory.md` §4.2 明确要求跨场 `[chat]` 节点参与 `survival_weight` 重排并携带 `distance`。只能优化其**实现效率**，不能移除语义。

## 4. 修复方案

> 全部为"消除重复/浪费"，不设节点数上限，不改任何业务语义。

### P0-1　节点身份归一（消除重复实例）— 收益最大

**目标**：让本场已有节点、跨场已并入节点一律命中缓存，不再走"新建"分支。

**做法**：

1. 新增统一索引 `window.__nodeIndex = new Map()`，键为 `String(serial_id)` 与 `String(node_id)` **双写**，两个键指向同一对象。
2. 在**所有**写 `nodeCache` 的位置同步登记该索引：
   - `static/js/3d_main.js:1607`（`fetchAndRenderGraph`）
   - `static/js/3d_main.js:1838-1839`（`updateNodeIncremental`）
   - `static/js/3d_main.js:2209`（`node_updated`）
   - `static/js/3d_main.js:2227`（`node_created`）
   - `static/js/3d_main.js:2276`（`node_deleted`，需同时删除两个键）
   - `static/js/3d_main.js:2338`（`openDrawer`）
3. `updateNodeIncremental` 的查找（`:1813`）改为：
   ```js
   let cacheNode = __nodeIndex.get(String(sid)) || __nodeIndex.get(String(nid));
   ```
4. 删除 `:1815-1821` 的 `for (const key in nodeCache)` 全表扫描（O(N²)）。
5. 并入图谱前（`:1844` 之后）保留按 `id` 的最终确认，作为兜底守卫。

**预期效果**：重复实例归零；`未找到缓存节点` 警告只在真正的跨场新节点出现。

### P0-2　斩断 URL 自动聚焦回环

**做法**：为 `static/js/3d_main.js:1768-1778` 增加一次性保护：

**后端**（`main.py:1315-1358` 的循环、`main.py:1587-1632` 同类循环）：

### P1-1　标签纹理复用（推荐方案 C：按变更来源分流）

**问题现状**：`createTextTexture` 有 4 处调用：

| 调用点 | 场景 | 频率 |
|---|---|---|
| `static/js/3d_main.js:3630` `nodeThreeObject` | 节点创建 | 每节点 1 次 |
| `static/js/3d_main.js:970` `updateEventHorizonVisibility` | **点击后更新视界** | **全图每节点 1 次** |
| `static/js/3d_main.js:1043` `hoverScaleNodeBloom` | 鼠标悬浮 | 每次悬浮 |
| `static/js/3d_main.js:1136` 悬浮结束还原 | 鼠标离开 | 每次离开 |

其中 **`:970` 是点击瞬间尖峰的直接来源**：它位于节点遍历中，点击后 `updateHighlight()` → `updateEventHorizonVisibility()` → 对全图每个节点重建一张纹理。

**现有亮度实现**（`:1320-1325`）：

```js
const weightValue = getVisualWeight(weight);
const brightness = 0.5 + (weightValue * 0.4);          // 0.5 ~ 0.9
const colorValue = Math.floor(255 * brightness);       // 128 ~ 229
const textColor = `rgb(${colorValue}, ${colorValue}, ${colorValue})`;
```

**方案 C 做法**：

1. **纹理缓存键去掉 weight**，只保留 `node_id + 截断模式`：
   ```
   key = `${node_id}|${isExpanded ? 'full' : 'short'}`
   ```
   同一节点的纹理一生只建 2 次，与权重变化彻底解耦。
2. 生成纹理时使用**固定满亮**（`colorValue = 255`），保留黑色阴影与底座。
3. 亮度改由材质承担：`sprite.material.color.setScalar(brightness)`，其中 `brightness = 0.5 + getVisualWeight(w) * 0.4`。
4. `:970` 处：保留 `shouldExpand`（截断/展开）变化时的纹理切换（这是真实结构变化），**其余情况只更新 `material.color` 与 `sprite.scale`，不碰 `material.map`**。

**视觉等价性验证**（数学上完全等价，非近似）：

```
原方案：纹理色 = 255 x 0.62 = 158，材质色 = 白(255) -> 最终像素值 158
新方案：纹理色 = 255，        材质色 = 158        -> 最终像素值 158
```

`getVisualWeight()`（`:343-346`）把 `1.0` 映射为 `0.3`，故 `weight=1` 时 `brightness = 0.5 + 0.3 x 0.4 = 0.62`，两方案结果一致。

**方案对比**：

| 方案 | 点击瞬间纹理重建数 | 视觉变化 | 显存改善 |
|---|---|---|---|
| 现状 | 250 张（1024x256 级） | — | — |
| B：不复用 + LRU | 250 张（权重全变 → 桶全失效） | 无 | 无 |
| A：全复用 | 0 张 | 亮度改为材质插值 | 最优 |
| **C：按来源分流** | **约 1 张**（仅被点中节点可能切换截断态） | **零变化（数学等价）** | **最优** |

> 方案 B 的致命缺陷：LRU 键若含 `weightBucket`，点击后所有节点权重都变、桶全失效，等于没省。
> 方案 C 取得 A 的收益，且视觉零变化，因此**推荐 C**。

### P1-1 补充：`skipLabels` 的正确边界（实施中的一次回归修正）

P1-1（方案 C）首次实施时，把「标签亮度纠正」错误地写进了 `if (!skipLabels && ...)` 分支内，导致**定时监控的亮度纠偏通道整体失效**。

#### 问题

```js
// 错误写法
if (!skipLabels && sprite && sprite.material) {
    const brightness = getLabelBrightness(weight);
    sprite.material.color.setScalar(brightness);   // ← 被 skipLabels 误伤
    // ... 纹理逻辑 ...
}
```

`socketio 广播 → node_updated → 权重变化` 之后，标签亮度停在旧值；定时监控（`3d_main.js:5451` 传 `skipLabels: true`）每秒跑一次却一个字都不改，唯一可靠的兜底通道被切断。而点击大重绘走 `skipLabels=false`，亮度是对的，因此问题**只在广播增量路径上表现为"亮度不纠正"**，隐蔽性强。

#### 正确边界

**`skipLabels` 只允许跳过 GPU 资源分配，绝不允许跳过 uniform / 材质状态更新。**

| 操作 | GPU 分配 | 是否受 `skipLabels` 约束 |
|---|---|---|
| `material.color.setScalar()` | **零**（仅改 uniform） | ❌ 必须无条件执行 |
| `createTextTexture()` 新建纹理 | 每张数百 KB ~ 数 MB | ✅ 跳过 |
| 换 `material.map` / 重排 `scale`、`position` | 引用替换 + 矩阵计算 | ✅ 跳过 |

修正后的结构（`3d_main.js:1023-1070`）：

```js
// (A) 亮度：无条件执行，socketio 广播后权重变化的唯一兜底纠正通道
if (sprite && sprite.material) {
    sprite.material.color.setScalar(getLabelBrightness(weight));
}
// (B) 纹理 / 尺寸 / 位置：这才是 skipLabels 的本意
if (!skipLabels && sprite && sprite.material) { /* ... */ }
```

#### 验证结果

| 场景 | `skipLabels` | 亮度纠正 | 纹理创建 |
|---|---|---|---|
| 点击 / 进出视界 / 悬浮 | `false` | ✅ | 按需（0~1 张） |
| 定时监控兜底 | `true` | ✅ **（已恢复）** | **0 张** |

> 关键不变量：`skipLabels=true` 时 `createTextTexture` 调用数必须为 0，否则 P1-1 的显存收益会被抵消。此不变量已用 Node 模拟断言通过。

### P0-4　大股东视觉唯一性（后端 60/40 分配律违约）

**现象**：点击 2553 使其成为大股东，再点击 756，756 成为新大股东，但**视觉上 2553 的大小与明度没有降低**，看起来像「两个大股东」。

#### 语义前提：大股东唯一

系统的权重模型是严格的 **60/40 分配律**：

- **大股东**：唯一，是「当前被观测 / 检索到的那个节点」，固定 **60%**
- **其余全部节点**：按 `向量语义距离` × `节点层级深度` 形成的现有权重比例，瓜分剩余 **40%**
- 权重为 0 的节点消失在视界星空中
- **不存在「降级大股东 / 旧大股东」这个概念**——一旦大股东易主，原大股东即降为普通节点，按比例参与 40% 的瓜分

60% 的取值是为了贯彻「果由观测者定，果为观察者坍塌」：> 50% 才能在任何节点数量下保证**绝对控股**（最亮最大），同时保留 40% 不至于消灭其它节点。

#### 根因：后端凭空创造的「第二特权」

`core/database.py:1893` 曾有一个特殊分支：

```python
if node_info['current_weight'] > 0.585:
    new_weight = 0.58          # ← 违约：给旧大股东一个降级特权
elif total_weight_excluding_boss > 0:
    new_weight = weight_ratio * 0.40
```

该分支**同时违反三件事**：

| 违约项 | 说明 |
|---|---|
| **破坏分配律** | 2553 拿 0.58 + 756 拿 0.60 = 1.18，总权重超过 1.0 |

### P0-5　大股东三重圣光（`showDivineBeam` 不幂等 + 广播回声自触发）

#### 现象

本机拖动 `max_eyes` 滑杆后，大股东节点同时出现 **2~3 束叠加的神圣光柱**；而其它接收 Socket.IO 广播的客户端只有 1 束。**只有操作发起端异常。**

#### 根因链（三条独立路径叠加在同一节点上）

| 序号 | 触发路径 | 代码位置 | 是否仅本机 |
|---|---|---|---|
| ① | 滑杆 `change` 直接打光 | `3d_main.js:3722` → `:3728 showDivineBeam(bossNode)` | **是**（接收端没拖滑杆） |
| ② | 自己收到的 `nodes_updated` 广播走「远端跃迁」分支 | `3d_main.js:2243-2261` | 本机 + 接收端 |
| ③ | 后端 `emit_nodes_updated_batch` 双房间扇出 | `main.py:1925-1933` | 本机命中 2 次 |

**路径 ② 之所以对发起端生效，是一个真实的逻辑漏洞：** 滑杆 `change` 和 `promoteNodeWeight` 都**没有**登记 `lastLocalActionTime`，于是

```js
const isLocalActionCooling = (now - lastLocalActionTime) < 3000;   // → false
```

本机自己发起的动作被当成「远端跃迁」，于是额外打一束光，**还会抢镜头做 2 秒相机跃迁**。

**结构性缺陷（真正治本点）：** `showDivineBeam` 的 `activeBeam` 是**单槽引用**，只能「替换」不能「拒绝」。同一节点被多次触发时没有任何幂等约束，上游触发 N 次就叠 N 束光。原清理代码也只 `remove()` 不 `dispose()`，每束光泄漏一个 32 段圆柱几何体 + ShaderMaterial，与本文档主线排查的显存暴涨同源。

#### 为什么 `bak/` 看起来正常

逐行比对确认：`bak/` 的 `showDivineBeam`、`activeBeam`、滑杆 `change`、远端跃迁分支与本项目**完全一致**，`bak/` 同样没有登记 `lastLocalActionTime` —— 也就是说该缺陷在 `bak/` 中**同样潜伏**。

差别只在后端：`bak/main.py` 用 `sm.emit('node_updated', node)` 逐条全局发，**没有 `nodes_updated` 批量事件、没有双房间扇出**，本机最多收到 1 份，因此路径 ③ 不存在、②只触发一次，视觉上「看起来正常」。

**结论：本次 GPU 优化引入的 `nodes_updated` 批量 + 双房间推送，放大了原本潜伏的非幂等问题。**

#### 修复内容（A + B + D，纯前端，未触碰广播语义）

| 方案 | 位置 | 改动 |
|---|---|---|
| **A 幂等（治本）** | `3d_main.js:452-463` | `showDivineBeam` 开头按 `userData.nodeId` 判重：同节点且存活 → `restart()` 计时后 `return`，**绝不新建第二束** |

### P0-6　方案 B 的副作用：滑杆后大股东不再居中（已在 e 之上修正）

#### 现象

#### 根因：居中原本一直在「搭便车」

逐行比对 `bak/static/js/3d_main.js:2886-2905` 与本项目 `:3713-3736`，**滑杆 `change` 的代码完全一致，都只有 `promoteNodeWeight` + `showDivineBeam`，没有任何 `cameraPosition` / `calculateOffsetView` 调用。**

那 `bak/` 时代滑杆后为什么会居中？因为走了「远端跃迁」分支：

```
滑杆 change
  → promoteNodeWeight 发 /click
  → 后端广播回来 → 本机也收到
  → updateNodeIncremental 命中 :2243「远端跃迁」分支
  → :2302 calculateOffsetView(gNode, 350)
  → :2305 Graph.cameraPosition(camPos, lookAt, 2000)   ← 居中实际由它完成
  → :2322 showDivineBeam(gNode)                          ← 顺带又打一束光（即 P0-5 的多重圣光源）
```

**P0-5 的方案 B（`:3720` 登记 `lastLocalActionTime`）关闭了该分支** —— 多重圣光随之消失，但**居中也被一并关掉**。

| 路径 | 原位来源 | 修复后状态 |
|---|---|---|
| 点击节点 | `:4005` / `:4090` 独立 `cameraPosition` | 正常 |
| 首帧事件视界 | `:1922` `calculateOffsetView(bossNode, 500)` | 正常 |
| **滑杆调 `max_eyes`** | 仅靠远端跃迁分支 `:2305` 搭便车 | **已断 → 本次修复** |

#### 修复（方案 1：滑杆路径显式居中）

`3d_main.js:3730-3739`，在 `showDivineBeam(bossNode)` 之后补上滑杆自己的居中：

```js
if (Number.isFinite(bossNode.x) && Number.isFinite(bossNode.y) && Number.isFinite(bossNode.z)) {
```

### P0-7　移动端专属：同节点出现两束圣光（PC 端正常）

#### 现象

- **PC 端**：点击节点、拖滑杆，均只有 **1 束**圣光 → 正确。
- **移动端**：点击节点、拖滑杆，**都是 2 束**；即便**节点位置不动、只拉滑杆**也复现。
- 两个动作（本机操作 / 作为客户端接广播）在移动端都表现为两次。

「同节点 + 位置不动 + 只拉滑杆也两次」这条现象很关键，它一次性排除了两个方向：

- 不是**大股东被切换**（否则两束光位置会不同）
- 不是**节点对象被替换**导致 `__lastClickTime` 丢失（只拉滑杆不涉及节点对象替换）

#### 排除的候选（逐个核实，均非原因）

| 候选 | 核实结论 |
|---|---|
| 1 秒定时监控器 `:5479` | ❌ 只改 `opacity` / `material.color` / 纹理，**从不调用 `showDivineBeam`**，不建任何 mesh |
| `updateEventHorizonVisibility` | ❌ 同上，纯材质更新；`skipLabels` 只影响纹理是否换 |
| `handleNodeClick`（`:3360`） | ❌ **死代码**：全项目（js + html）仅此一处定义、零调用 |
| `horizon_updated` 广播（`:2347`） | ❌ 只做 `triggerCosmicFlash()` + `updateHighlight()` |
| `promoteNodeWeight` 内部 | ❌ 仅 `:1586` 登记 `lastLocalActionTime` + 发 `/click`，不打光 |
| 双击检测逻辑本身 | ❌ 与 `bak:3107-3124` **逐行一致**，非本次改动引入 |
| `onNodeClick` 重复绑定 | ❌ `.onNodeClick(...)` 是 setter（覆盖语义），且全文件仅绑定一次 |

> 结论：**这是 `bak/` 时代就存在的移动端隐性缺陷**，与本次显存/居中等修复无关。`bak/` 因为没有幂等保护、叠光更杂乱，反而不容易被单独察觉。

#### 根因：幂等判重被 `activeBeam = null` 竞态击穿 + 触屏事件双发

**环节 1 —— 移动端一次操作会走到 `showDivineBeam` 两次。**

`3d-force-graph.min.js` 内部用 `pointerup` 派发点击：

```js
n.domElement.addEventListener("touchstart", N, {passive:!1})
n.domElement.addEventListener("touchend", k)
... .clickAfterDrag(!1).onClick(...)
```

触屏下同一次点按会走两条派发链（`pointerup` 原生 + `touchend` 派生的合成 `click`）；滑杆则是部分移动浏览器在 `touchend` 时补发一次 `change`（`input → change → touchend → change`）。**PC 端鼠标 `click` 不会重复派发，所以不暴露。**

**环节 2 —— 原有的幂等判重挡不住，因为它依赖 `activeBeam` 的存活状态：**

```js
if (activeBeam && !activeBeam.userData.isDead &&
    activeBeam.userData.nodeId === targetId) { restart(); return; }   // 判重
```

而 `activeBeam` 会被渲染循环**静默置为 null**：

```js
if (activeBeam) {
    const isAlive = activeBeam.userData.animate();   // elapsed > 3500ms → 内部 dispose 并 return false
    if (!isAlive) activeBeam = null;                 // ← 置空，但判重条件就此失效
}
```

移动端帧率低、`requestAnimationFrame` 被系统节流，`animate()` 里 `Date.now() - startTime` 一跳就可能越过 `duration`(3500ms)，光柱"提前死亡"。**此时 `activeBeam === null`，判重整体跳过，第二次派发直接新建 mesh → 第二束光。** 位置相同，因为节点没变。

**环节 3（附带缺陷）—— `beamAnimationId` 从不重置。**

`if (!beamAnimationId)` 一旦为真就不再进入，但循环在 `activeBeam` 判死后仍在 `requestAnimationFrame` 上空转，既浪费每帧开销，也没有正确的新循环启动/停止机制。

#### 修复（四处，均为纯防御性改动，不动业务逻辑）

**① 与 `activeBeam` 状态解耦的时间窗判重**（根治环节 2）

新增状态（`:391-397`）：

```js
const __BEAM_DEDUP_MS = 400;                      // 同节点建光抑制窗口
let __lastBeamStart = { id: null, t: 0 };         // 最近一次真正建光/续期的节点与时刻
```

`showDivineBeam` 开头（`:464-480`）：

```js
const targetId = node.id || node.node_id;
const nowMs = Date.now();

// 同节点、窗口内 → 完全丢弃：不续期、不新建，避免任何视觉叠加
if (__lastBeamStart.id === targetId && (nowMs - __lastBeamStart.t) < __BEAM_DEDUP_MS) {
    return;
}
// 原有幂等：同节点存活 → 只重启计时（并登记时刻，挡住紧随其后的重复派发）
```

建光成功后也登记（`:693`）：`__lastBeamStart = { id: targetId, t: nowMs };`

**关键设计**：这个窗口**完全不看 `activeBeam`**，所以即便光柱已被判死、`activeBeam` 已为 null，重复派发依然被拦下。400ms 小于人眼可辨间隔，快速切换不同节点不受影响（不同 `targetId` 直接放行）。

**② 修正渲染循环的启停**（环节 3，`:699-710`）

```js
if (activeBeam) {
    beamAnimationId = requestAnimationFrame(renderLoop);
} else {
    beamAnimationId = null;   // 无光柱：停止循环，省掉空转的每帧开销
}
```

**③ `animate()` 增加存活守卫**（防访问已释放资源，`:654-660`）

```js
// 注意：失效标记由 disposeBeam 写在 userData.isDead 上，必须取 userData 下的字段。
if (beamMesh.userData.isDead) return false;
```

用闭包变量 `beamMesh` 而非 `this`，与下方 `disposeBeam(beamMesh)` 一致，不依赖调用方的 `this` 绑定。

> 此处修正过一次笔误：初版写成 `beamMesh.isDead`，而 `disposeBeam` 系设在 `beam.userData.isDead`（`:406`），守卫会永远读到 `undefined` 而静默失效。已核对并改正。

**④ 滑杆 `change` 触屏去抖**（`:3746-3756`）

```js
let __sliderChangeLock = 0;
slider.addEventListener('change', (e) => {
    const nowMs = Date.now();
    if (nowMs - __sliderChangeLock < 300) {
        console.log('[望远镜] 忽略重复的 change 事件（触屏双发）');
        return;
    }
    __sliderChangeLock = nowMs;
    ...
```

300ms 窗口同时挡掉「重复的两束光」和「重复的两次 `/click` 请求」。

#### 为何不选「改双击检测」

`:3953-3964` 的 `__lastClickBlocked` 分支确实存在「视界外节点第二次点击被放行」的路径，但**修它会破坏「视界外双击强制点击」这个既有功能**，且只覆盖点击、不覆盖滑杆。时间窗方案对两者统一生效，且不需要触碰交互语义。
